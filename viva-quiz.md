1. **What problem does the project address?**  
   It structures project selection, milestones, report drafting, and weekly status updates for final-year teams.

2. **Who is the target user?**  
   Final-year CSE project teams. Confirm whether your own user evaluation supports this choice.

3. **Why use HTML, CSS, and JavaScript?**  
   They make a lightweight prototype that can run directly in a browser without server setup.

4. **How is the scorecard calculated?**  
   `0.4 × feasibility + 0.3 × impact + 0.3 × (6 − risk)`. Each input is on a 1–5 scale.

5. **Why invert the risk score?**  
   A higher risk should reduce the final score, so the formula uses `6 − risk`.

6. **Does the app use a live AI model?**  
   No. It uses fixed templates and keyword rules. The project brief requires research into AI tools; document external tools separately if you actually use them.

7. **What are the limitations of weekly automation?**  
   Keyword rules can misclassify a sentence, miss context, or treat a future plan as completed. Human review is required.

8. **How do you avoid fabricated citations?**  
   The app does not generate citations. Students must find and verify original sources and record bibliographic details.

9. **What testing is needed?**  
   Check scoring, form inputs, tabs, drafting, categorization, checklist persistence, exports, and mobile layout; record actual results.

10. **What would you improve next?**  
    Potential improvements include user testing, configurable rubrics, accessible design refinements, shared storage, and optional AI with explicit verification safeguards.

11. **How is user data handled?**  
    The prototype runs locally and does not send data to a server. Checklist state uses browser local storage; users should export important data.
